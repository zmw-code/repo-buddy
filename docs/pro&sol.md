## 2026-09-27

### P2 · 需求文档评审：10 处会误导实现或影响 S1 可信度的表述

- **问题**：文档自称"可直接作为 coding agent 的输入"，但存在字面矛盾与工程缺口。最要命的四条：
  ①设计原则 3「绝不修改任何本地文件」与 S2 的 `git add`（写 index）字面冲突，较真的 agent 会在实现时卡壳；
  ②S1 只有场景描述、没有工程核心（规则匹配语义、增量统计口径），而它是 MVP 主切入点；
  ③MVP 清单顺序把右键菜单排在前，而它是 MVP 中唯一碰注册表、唯一有杀软误报风险、对核心差异化零贡献的模块；
  ④v0.1 验收要求"全程零命令输入"，但右键菜单既然可跳过，跳过时该验收不可能达成。
- **解决**：随评审把 9 类修订直接写入正文（18.1–18.9），第 10 类明确记录"看过但不改"（18.10）；
  逐条"原文 → 修改后"对照见 `docs/评审修订记录.md`：
  原则 3 改为"不动**工作区**文件"、把 git 内部数据与注册表写操作限定为"用户显式发起"；
  S1 补 4 条实现要点（用现成 gitignore 语义库 + `git check-ignore` 抽样对拍；候选规则先排除已有规则；
  影响预览取增量语义并按规则缓存；应用后跑 `git ls-files -c -i --exclude-standard` 只提示不代做）；
  MVP 顺序改为 core 先行、右键菜单压到最后；验收口径与"可跳过右键菜单"解耦；
  JSON 契约加 `schema` 字段并标 unstable 至 v1.0；`.gitignore` 备份方案换成"写前 diff + 会话内一键撤销"；
  补注册表 `%1`/`%V` 经典坑；修正文档头状态行与 README 里引用的不存在的 16.5 节。
- **证据**：`docs/评审修订记录.md`（原需求文档第十八节，含"原文 → 修改后"对照）。

### P5 · 23:33 · 风险 #1（中文宽字符对齐）没有验证手段

- **问题**：需求文档把中文宽字符对齐列为**最大技术风险**、要求第一周做出验证 demo，
  但仓库里只有一个纯标准库骨架，没有任何量具 —— 而这个坑决定 TUI 里所有列表、边框、表格能否对齐。
- **解决**：新增 `repobuddy cjk-check`：11 项自动断言（宽度模型 / 盒线闭合 / 表格列对齐 / 按宽度截断）
  + 一节"按字节数对齐"的反例 + 一节供人眼确认的目视材料；
  配套 `internal/tui/width.go` 提供 `DisplayWidth` / `PadRight` / `PadLeft` / `Truncate`，
  作为后续所有对齐的唯一入口。
- **证据**：`go run . cjk-check` → 自动断言 11 项全通过（退出码 0）；commit `818dfe8`。

### P6 · 23:34 · 自检程序自己的量具写错了 3 处

- **问题**：首轮运行 `cjk-check` 报 8 项 FAIL，根因却在**检查器**而非被测对象：
  ①样本字符串带了引号（`"abc"`），期望值却按不含引号算 → 6 项虚报失败；
  ②列起点误用 `allEqual` 判定（各列起点本就应该互不相同，该判的是"三行之间是否一致"）→ 1 项虚报失败；
  ③盒线字符期望值数错（`┌─┐│` 是 4 个字符，写成了 5）→ 1 项虚报失败。
- **解决**：样本改裸字符串、列起点改判"三行一致且列数为 3"、期望值改 4。
  教训：**体检工具本身也要先被体检**（先用正例/反例自证，再拿去判别人的错）。
- **证据**：修复前后 `go run . cjk-check` 输出对比（8 项 FAIL → 11 项 PASS）。

### P9 · 23:45 · 自检报告的排版自己错位（用户实机发现）

- **问题**：报告第 1 节末尾两行（`Emoji` / `歧义字符`）的"报告"没对齐 —— 报告的列宽用了 `fmt %-12s`，

### P10 · 23:49 · 已知边界：东亚歧义字符口径不一致会让模型失真（处置已定，风险留档）

- **问题**：`┌ ─ ┐ │`、`① ± ° →` 属 Unicode「东亚歧义（Ambiguous）」类，同一字符在英文环境按 1 格、
  东亚环境按 2 格都合规。程序与终端口径不一致时，边框会歪成锯齿。
  实测：把 go-runewidth 切到东亚宽口径（`RUNEWIDTH_EASTASIAN=1`）后重跑自检，立刻 2 项 FAIL：
  盒线字符期望 4 实测 8；方框各行宽度变成 `[62 33 33 33 62]`。
- **解决**：默认沿用 `EastAsianWidth=false`（与 Windows Terminal 实测一致：方框右边框成一条直线，
  已由用户实机目视确认）；口径写进自检输出第一行（可复现），并在报告第 4 节写明两条退路：
  改用 ASCII 边框（`+---+`）或启动时探测。换字体 / 改字号 / 缩放窗口后需重跑自检。
- **证据**：`RUNEWIDTH_EASTASIAN=1 go run . cjk-check` → 失败 2 项、`[62 33 33 33 62]`；
  默认口径 → 11 项全通过。

### P11 · 23:50 · MVP 第一项 `scan` 的契约口径：文档写「三类」，但会丢 S2 需要的信息

- **问题**：需求文档 10.1 / 10.2 / 11 都写 `scan` 输出「未跟踪 / 已修改 / 已忽略 三类」。
  可 `git status --porcelain` 的两位状态码**首列本来就是**「index 有改动」与「仅工作区有改动」的区分；
  按三类实现等于把这条信息丢掉，而 MVP 第 4 项（勾选暂存 + 提交）与 TUI 列表必须区分二者 ——
  丢掉就要在 TUI 阶段返工，且「哪些已暂存」正是提交流程第一步要展示的东西。
- **解决**：按**四类**实现（多一个 `staged`），并把口径落成可核对的文本：
  加评审修订 18.11（说明属增补而非破坏：原三类口径不变、只多一个数组与一个计数字段、schema 仍为 1）；
  10.1 / 10.2 / 11 三处同步；完整「输出码 → 归类」对照表写进 `docs/json-contract.md`。
  staged 与 modified **互斥**（首列非空即 staged，`MM` 的同时存在未暂存改动这一信息保留在 `code` 里不丢）。
- **证据**：`docs/评审修订记录.md` 18.11；`docs/json-contract.md`；commit `a09727e`（23:55）。

### P12 · 23:52 · 端点测试会随本机 git 环境漂移：同一份代码换台机器就红

- **问题**：`scan` 的端到端测试要在临时目录里造仓库，但结果受本机全局配置摆布 ——
  `core.autocrlf`（影响工作区是否"已修改"）、全局 `core.excludesFile`（凭空多出"已忽略"条目）、
  缺 `user.name` / `user.email`（commit 直接失败）。这类测试"本机绿、别处红"，是最难查的一类假阳性。
  附带：`git status` 默认会把中文名转义成 `\344\273\223...`，直接按行切会解析出错。
- **解决**：测试内用 `GIT_CONFIG_GLOBAL` 把全局配置指到临时文件、`GIT_CONFIG_NOSYSTEM=1` 关掉系统级配置、
  提交显式带 `-c user.name/-c user.email`；产线代码一律用 `git status --porcelain -z` 的 NUL 分隔格式，
  路径不做引号转义，中文 / 空格 / `&` 都能原样拿到。
- **证据**：`go test -count=1 -v ./internal/core/` → 5 项全通过（分类口径 / 重命名与不合格式记录 /
  临时仓库端到端 / 非仓库路径 / JSON 原样输出）。本机全局 ignore 文件不可读时 git 会打 warning，但不影响结果。

### P13 · 23:54 · `--json` 把 `pro&sol.md` 写成 `pro\u0026sol.md`

- **问题**：Go 的 `encoding/json` **默认做 HTML 转义**，`&` `<` `>` 会被写成 `\u0026` 等。
  解码结果虽然一样，但 `--json` 的用途之一就是人眼核对与写进契约文档 ——
  本项目自己的文档名 `pro&sol.md` 恰好踩中，输出里看到的是 `pro\u0026sol.md`，像是文件名被改了。
- **解决**：改用 `json.Encoder` + `SetEscapeHTML(false)`（仍是 2 空格缩进、末尾带换行）；
  加回归测试 `TestReportJSON`（断言路径原样出现 + 必须是合法 JSON + `counts` 与四个数组长度一致）；
  契约文档的"共同约定"补一条：不做 HTML 转义。
- **证据**：修复前 `go run . scan --json | Select-String pro` → `docs/pro\u0026sol.md`；
  修复后 → `docs/pro&sol.md`。

### P14 · 23:56 · 验收退出码被 `go run` 改写（工具坑，不是产品 bug，但会误导验收）

- **问题**：`repobuddy scan --nope` 应当以退出码 2 结束（参数错误），实机 `go run . scan --nope`
  打印 `exit status 2`，而 PowerShell 的 `$LASTEXITCODE` 是 **1** —— `go run` 自己统一把非零退出码改写成 1。
  照这个方法验收退出码，会把"参数错误(2)"和"运行失败(1)"看成同一回事。
- **解决**：退出码一律用编译后的 exe 验收（`go build -o repobuddy.exe .` 后再跑），
  或在验收记录里写明"经 `go run` 时退出码不可信"。产品代码的退出码约定本身没问题（0 成功 / 1 失败 / 2 用法错误）。
- **证据**：`go run . scan --nope` → `exit status 2` + `$LASTEXITCODE=1`；
  换成编译后的 exe 复验：`scan` → 0、`scan --nope` → 2、`scan <非仓库目录>` → 1、
  `cjk-check` → 0、未知子命令 → 2（与设计一致）。
